# 응답 지연

> 전제: 개발 서버 1대(`dev-cking-app`), Docker Compose, Cking-BE `deploy.sh` 배포

응답 시간 p95가 1초를 넘고 10분 지속될 때(헬스체크 제외).

## 뜻하는 것

요청 상위 5%가 1초 넘게 걸린다. 7일 p95 최대는 0.66초다.

## 먼저 볼 곳

1. **크킹 앱 → URI별 p95**: 특정 URI인지 전체인지
2. **크킹 앱 → Hikari 연결, GC 정지 시간, CPU**
3. **크킹 서버 → CPU 사용률, EC2 CPU 크레딧 잔량, 여유 메모리, swap 입출력, RDS CPU**

## 원인별 대응

### 1. 특정 URI만 느림

느린 쿼리·외부 API 호출일 가능성이 크다. 로그와 URI로 BE 이슈를 만든다.

### 2. 전체가 느림

- CPU 크레딧이 0 근처: t4g.small이 기본 성능(20%)으로 묶였다. 요청이 몰린 상황이면 지나가길 기다리고, 반복되면 인스턴스 크기 검토
- swap 입출력이 많음: 서버 메모리 부족. [서버 여유 메모리](cking-memory-available.md)
- GC 정지가 큼: 힙 부족. **크킹 앱 → 힙·힙 밖** 추세로 BE 이슈
- Hikari 대기: [DB 연결 대기](cking-hikari-pending.md)
- CPU가 높고 크레딧은 남음: 요청량이 서버 처리 한계에 닿았다. 서버 1대(t4g.small)는 응모 초당 250부터 CPU 83% 이상이고 DB 연결 10개를 다 쓴다(부하 테스트 2차). 요청이 몰린 상황이면 지나가길 기다린다
- **크킹 앱 → Redis 명령 평균 시간 (앱 쪽)**이 큼: Redis가 늦게 응답한다. 앱에 Redis 명령 제한 시간이 없어(Lettuce 기본 60초) 요청이 그만큼 묶인다. Redis 상태는 [응모 실패 (Redis 쓰기 거부)](cking-redis-rejected.md#먼저-볼-곳)의 명령으로 본다

## 해결 확인

**크킹 앱 → URI별 p95**가 1초 아래로 내려오고 경보가 풀린다.

## 하면 안 되는 것

- 원인을 보기 전에 앱을 재시작하지 않는다. 재시작 직후에는 JIT 컴파일 전이라 오히려 느리고, 원인이 그대로면 다시 느려진다

## 운영에서 다른 점

- 운영 앱 서버 전체로 판단한다. `instance`별로 나눠 한 서버만 느리면 그 서버의 CPU·메모리를 보고, 원인을 본 뒤 교체한다
- 운영 앱 서버는 c6g.large(버스터블 아님)라 CPU 크레딧이 없다. 전체가 느리고 CPU가 높으면 서버 그룹이 서버당 분당 요청 6,300건 목표로 늘리는 중인지 본다(최대 4대)
- RDS·ElastiCache CPU는 CloudWatch로 본다
- 정각 직후 약 1초 동안의 지연은 알려진 현상이다. RDS는 부하와 상관없이 매시 정각 약 2초 동안 관리 작업으로 vCPU를 거의 다 쓰고, 그 사이 응모 경로의 이벤트 캐시(5초 만료)가 비면 들어온 요청이 모두 DB를 읽는다. 운영 측정(부하 테스트 3차, c6g.large 2대·RDS 다중 AZ, 초당 150)에서 정각 0초 응모 API 최대 253ms, 1초 뒤부터 200ms 이하, DB 반영 1초 이내 99.78%, 실패 0이었다. 앱 서버 steal은 c6g.large로 바꾼 뒤 0%다. 이 경보는 10분 지속 조건이라 정각 지연만으로는 울리지 않는다
