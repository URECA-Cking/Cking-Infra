# DB 연결 대기

> 전제: 개발 서버 1대(`dev-cking-app`), Docker Compose, Cking-BE `deploy.sh` 배포

`hikaricp_connections_pending > 0`이 5분 지속될 때.

## 뜻하는 것

DB 연결 풀(Hikari 기본 10개)이 모두 사용 중이라 요청이 연결을 기다리고 있다. 30초 안에 연결을 못 얻으면 요청이 실패한다. 7일 최대값은 0이다.

## 먼저 볼 곳

1. **크킹 앱 → Hikari 연결, 연결 획득 평균 시간**: active가 10에 붙어 있는지
2. **크킹 서버 → RDS CPU, RDS 연결 수**
3. AWS 콘솔 RDS → 이벤트(재부팅·유지 관리), Performance Insights(켜져 있으면)

## 원인별 대응

### 1. 느린 쿼리가 연결을 오래 잡음

RDS CPU가 높거나 특정 URI p95가 높다. 느린 쿼리 로그·URI로 BE 이슈를 만든다.

### 2. 요청이 몰림

요청량이 평소보다 크게 늘었다. 지나가면 풀린다. 반복되면 풀 크기·쿼리 개선을 BE 담당과 정한다.

### 3. RDS 문제

RDS 이벤트에 재부팅·장애 조치가 있거나 연결 수가 0이다. RDS가 돌아오면 앱이 다시 연결한다.

## 해결 확인

**크킹 앱 → Hikari 연결**의 대기(pending)가 0으로 돌아온다.

## 하면 안 되는 것

- 풀 크기를 늘리는 것으로 먼저 대응하지 않는다. 원인이 느린 쿼리면 DB 부하만 커진다. db.t4g.micro는 연결 수 여유가 적다

## 운영에서 다른 점

- 경보는 서버별로 울린다. 한 서버만이면 그 서버의 느린 요청, 전체면 RDS 쪽이다
- 풀은 서버마다 10개라 RDS 연결은 10 × 서버 수이고, 교체 중에는 서버가 최대 2배가 된다. RDS 연결 수는 CloudWatch로 본다
- RDS는 db.t4g.small 다중 AZ다. 이벤트에 장애 조치가 있으면 끝난 뒤 앱이 같은 엔드포인트로 다시 연결한다
