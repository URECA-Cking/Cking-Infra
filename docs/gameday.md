# 장애 주입 게임 데이

운영 환경에 지속 부하를 걸고 장애 5가지를 차례로 넣어, 장애마다 실패 요청 수, 끊긴 시간, 회복, 첫 경보까지 걸린 시간, 응모 유실 여부를 측정한다. 정식 오픈 전(사용자 없음) 2026-10-28 UTC에 1부·2부로 나눠 진행했다. 시각은 모두 UTC다.

## 1. 환경과 방법

| 항목 | 값 |
|---|---|
| 앱 서버 | c6g.large 2대(2a·2b), 오토스케일링 그룹 2\~4대, 그룹 헬스 체크 ELB |
| DB | RDS MySQL 8.4 db.t4g.small 다중 AZ |
| Redis | ElastiCache Valkey 7.2 cache.t4g.small 2노드(2a 주, 2b 복제), 자동 장애 조치 |
| 앱 헬스 체크 | ALB 대상 그룹 `/readyz`(10초 간격, 2회 실패 시 비정상). `/readyz`는 앱 상태와 DB·Redis 연결을 함께 본다 |
| 부하 | 부하 테스트 실행기([`loadtest/`](../loadtest/README.md)), k6 c7g.medium(운영 프라이빗 서브넷). 예열 50,000건 뒤 지속 응모 초당 80 |
| 데이터 | 크리에이터 5, 회원 10,000(조합 50,000), 조합당 시작 잔액 100 |
| 장애 주입 | 지속 부하 시작 기준 정해진 분에 AWS CLI로 주입([`loadtest/gameday/`](../loadtest/gameday/)). 부하 시나리오는 `loadtest/scenarios/gameday.toml`(1부)·`gameday2.toml`(2부) |
| 판정 | 요청별 k6 기록과 DB·Redis 대조, Prometheus 지표, Grafana·CloudWatch 경보 이력, ElastiCache 이벤트 |

## 3. 장애별 결과

### 장애 1: 앱 서버 1대 종료

- 그룹의 `terminate-instance-in-auto-scaling-group`(희망 용량 유지)으로 종료했다. 그룹이 ALB에서 먼저 빼고(등록 해제 대기 90초) 종료해 실패가 없었다. 갑자기 죽는 경우와 다르다
- 남은 1대가 초당 80을 받는 동안 응모 p95 최대 18ms(20:50\~20:59)

### 장애 2: RDS 재부팅 + 강제 장애 조치

- RDS 재가용 21:01:35(92초), 주 DB 2b → 2a
- 응모는 Redis가 먼저 받으므로 DB가 끊긴 동안에도 접수됐고, DB 반영만 밀렸다가 따라잡았다(Stream 밀림 최대 298)
- 클라이언트는 21:00:14\~16에 보낸 49건의 응답을 받지 못했다. 49건 모두 서버가 처리했다
- **헬스 체크 결함:** `/readyz`가 DB까지 봐서 DB가 끊긴 동안 2a 서버가 ALB 비정상이 되고, 그룹 헬스 체크가 ELB라 그 서버를 교체했다(새 서버 21:02:43, 2a). 공유 의존성 장애가 멀쩡한 앱 서버 교체로 번진다(6절)

- 장애 조치 뒤 지연은 4절

### 장애 4: 앱 컨테이너 메모리 초과

- 2b 서버의 컨테이너 메모리 상한을 700MiB로 내려 커널 OOM → 재시작 1회 → 1,800MiB로 되돌렸다
- 21:31:23\~36에 보낸 529건이 502. 죽은 컨테이너로 ALB가 계속 보내다가 비정상 판정 뒤 끊었다
- 컨테이너만 재시작돼(`unless-stopped`) 서버 교체는 없었다

### 장애 5: 2a 서브넷 앱 계층 차단

- 임시 NACL로 퍼블릭 서브넷 → 2a 앱 서브넷 8080을 막았다
- 21:38:28\~50에 보낸 요청 중 871건이 504(ALB 대상 연결 시간 초과 10초). ALB가 2a 대상을 비정상으로 본 뒤 2b 1대가 초당 80을 받았다(실패 0)
- 그룹은 비정상 2a 서버를 교체하면서 새 서버를 다시 2a에 띄웠고(21:40:35), 새 서버도 막혀 다시 2a에 띄웠다(21:46:27). 그룹은 가용 영역 장애를 모르고 영역 균형을 맞추려 한다

## 4. Valkey 장애 조치 뒤 응모 지연

장애 조치 뒤 약 5분 30초 동안 모든 성공 응모가 약 250ms 늦었다(실패 0).

**원인:** 응모 성공 응답 전 복제 확인(BE #725). 응모 Lua 뒤 같은 연결에서 `WAIT 1 250`을 보내고, 제한 시간 안에 확인하지 못해도 성공으로 응답한다(운영 설정: 켬, 250ms). 장애 조치 뒤 옛 주 노드가 복제 노드로 돌아올 때까지 복제 노드가 없어, 성공 응모마다 250ms를 다 기다렸다.

| 근거 | 내용 |
|---|---|
| 지연 크기 | p50 263ms = 대기 상한 250ms + 평소 응답 약 12ms. 성공 응모 100%가 250ms 이상 |
| 지연 범위 | 서버 측 응모 p95가 21:25\~21:30 488ms로 일정(히스토그램 250\~500ms 구간). 두 서버가 초당 40씩 받았고 요청 100%가 느려 두 서버 모두 해당 |
| 지연 기간 | 장애 조치 완료(21:23:44, 복제 노드 0개) 뒤 시작해 21:29:50에 끝났다. `WAIT`는 복제 노드가 확인을 돌려줘야 시간 초과 전에 끝나므로, 21:29:50은 옛 주 노드가 복제 노드로 붙어 확인을 돌려주기 시작한 시각이다. 옛 주 노드 복구 이벤트(21:29:14) 뒤이고, ElastiCache의 복구 완료 표시(21:30:44)보다 앞이다 |
| 로컬 재현 | Valkey 7.2 주·복제 노드에서 복제 노드가 있으면 `WAIT 1 250` 0.2ms, 복제 노드를 없애면 확인 0으로 시간 초과까지 기다린다. 옛 주 노드를 복제 노드로 다시 붙이면 동기화가 끝나 확인을 돌려줄 때부터 다시 바로 끝난다 |

- 초당 80에서 SLO(p95 1초) 안이다. 복제 노드가 없을 때는 기다려도 확인될 수 없으므로, 복제 노드 수를 보고 대기를 건너뛰는 방안이 있다(7절)

## 5. 경보

| 장애 | 첫 경보 | 주입 → 경보 |
|---|---|---|
| 1 앱 서버 종료 | 없음 | - |
| 2 RDS 장애 조치 | Grafana `ERROR 로그` 21:01:10 | 약 67초 |
| 3 Valkey 장애 조치 | Grafana `ERROR 로그` 21:24:10, CloudWatch `prod-cking-alb-no-healthy-target` 21:26:16 | 약 47초 |
| 4 앱 메모리 초과 | 없음 | - |
| 5 2a 차단 | 없음 | - |

- 장애 4·5는 ALB 5xx가 몰렸지만 경보가 없었다. `prod-cking-alb-5xx`(당시 5분 합계 비율 > 5%) 기준으로 1분 529건·848건이 5분 요청 약 24,000건의 2.2%·3.6%에 그쳤다. 게임 데이 뒤 1분 비율 > 5%가 한 번이면 울리도록 바꿨다(Infra #244, #267). 게임 데이 지속 부하 49분에 대면 장애 4(11.0%)·5(17.8%)가 있던 두 분에만 울린다. Grafana `서버 오류 증가`는 앱 지표라 ALB가 돌려준 502·504를 보지 못한다
- `처리 실패 누적`이 평소 부하에서도 울렸다(20:56, 21:29, 21:48). 조건이 미처리 메시지 개수 > 0 10분이라, 계속 들어오는 부하에서는 미처리 1\~3건이 늘 있다. 게임 데이 뒤 가장 오래된 미처리 메시지의 나이가 10분을 넘을 때 울리도록 바꿨다. 정상이면 실패 메시지도 약 9분 안에 재처리되거나 Dead Stream으로 빠진다
- `응모 실패 (Redis 쓰기 거부)`가 21:30:10에 울렸다(5분 동안 거부 1건). 같은 5분 동안 응모는 모두 성공해 응모 쓰기가 거부된 것은 아니다

## 6. 찾은 결함

| 결함 | 영향 | 대응 |
|---|---|---|
| ALB·그룹 헬스 체크가 DB·Redis까지 보는 `/readyz`를 함께 씀 | 공유 의존성 장애에 모든 서버가 비정상, 2분 넘으면 그룹이 멀쩡한 서버 교체(장애 2에서 1대) | ALB 헬스 체크를 앱 생존만 보는 `/livez`로 변경(BE #825, Infra #278). 장애 조치 재측정에서 `/livez`도 요청 스레드 고갈로 시간 초과돼 관리 포트(8081) liveness로 다시 바꿈(BE #835, Infra #290, 8절). 배포 자기 검사는 `/readyz` 유지 |
| 그룹이 가용 영역 장애를 모름 | 막힌 영역에 새 서버를 계속 띄움 | 미적용. 안: 영역 이동(ARC zonal shift) 또는 그룹 서브넷에서 영역 제외 절차를 런북으로 |
| ALB 5xx 경보가 5분 비율 | 반 용량이 수십 초 끊겨도 경보 없음 | 1분 비율 한 번 초과로 변경(Infra #244, #267) |
| `처리 실패 누적`이 개수 기준 | 평소 부하에서 오경보 | 가장 오래된 미처리 메시지의 나이 10분 초과로 변경(앱 지표, BE #815, Infra #268) |
| 복제 노드가 없을 때도 복제 확인 대기 | 장애 조치 뒤 수 분간 응모 +250ms | 미적용(SLO 안) |

### 서비스 포트 `/livez`가 시간 초과된 이유

- 장애 조치 동안 DB·Redis를 기다리는 요청이 Tomcat 요청 스레드 200개를 모두 잡았다(고갈된 서버에서 사용 스레드 200/200, Hikari 연결 대기 191\~194). `/livez`도 같은 스레드를 기다려 ALB 헬스 체크(10초 × 2회)에 걸렸다. Valkey는 두 서버가 함께 걸려 정상 대상이 0이 된 구간이 있었다
- v1.4.0 RDS는 비정상 0이었다. 사용 스레드 200은 15초 수집 한 번에만 보였고 연결 대기 시간 초과는 0이었다(#817 되돌림 회차는 한 서버가 수 분간 200). 이 회차는 AWS 장애 조치도 빨라(시작 6초·완료 30초, #817 되돌림 회차 74초·40초) 차이를 코드 변경 하나로 보지 않는다
- 관리 포트(8081)는 별도 웹 서버라 요청 스레드가 고갈돼도 응답한다(BE #835, Infra #290). 같은 PR에서 Hikari 연결 대기를 30초 → 5초로 줄여, 연결을 못 얻은 요청이 빨리 실패하고 스레드를 놓는다. 대가로 Valkey 장애 조치의 실패 수는 457 → 2,354로 늘었고 지연은 p99 24.4초 → 7.3초로 줄었다

### v1.4.1 RDS: 응답 없는 옛 주 DB에 연결이 묶임

- 장애 조치 뒤 옛 주 DB가 응답도 RST도 없이 사라졌다. 쿼리를 보내 둔 Hikari 연결 10개(서버마다 풀 전체)가 응답을 끝없이 기다렸고, 커널 TCP 재전송 한도(`tcp_retries2=15`, 약 15분)가 지나서야 끊겼다. 그동안 DB를 쓰는 요청은 연결 대기 5초 뒤 모두 500이었다(약 15분 50초)
- 관리 포트 liveness는 DB를 보지 않아 서버는 healthy로 남고 교체되지 않았다
- JDBC `socketTimeout`이 없어 드라이버가 먼저 끊지 못한 것이 원인이라 20초로 뒀다(BE #841). 앱이 정한 최장 대기(`GET_LOCK` 15초)보다 길고, 운영 부하(지속·마감 몰림·추첨·동시 요청)의 느린 쿼리 로그(1초 초과)에 앱 요청 쿼리는 없었다(1초를 넘은 것은 Flyway 잠금 대기 최대 1.92초와 부하 테스트 시딩뿐). 응답 없는 DB에서 실패까지는 설정값의 2배였다(Connector/J 9.7.0, 로컬에서 MySQL 컨테이너를 멈춰 40.02초). 대가로 행 잠금 대기(InnoDB 기본 50초)가 이 시간을 넘는 쿼리는 연결이 끊기며 실패한다
- v1.4.2 재측정: DB 요청 막힘 약 45초, 최대 응답 40.07초(= 20초 × 2). 앱 로그에 `Communications link failure`가 남았고, 연결 대기 시간 초과는 787건
