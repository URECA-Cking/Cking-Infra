# 부하 테스트 결과

응모 → Redis Lua → Stream 소비 → DB 반영 → 마감 → Snapshot·추첨 경로가 어디까지 버티는지, 어느 구간이 먼저 병목이 되는지, 부하 중에도 정합성이 지켜지는지를 측정한다. 정합성은 성능보다 우선한다.

각 차수의 숫자는 그 시점의 구성(2절)에서 잰 값이다. 이후 구성이 바뀌어도 고쳐 쓰지 않고, 다시 재면 차수를 추가한다.

## 1. SLO v0

부하는 도착률 방식(k6 `ramping-arrival-rate`)으로 준다. SLO 판정은 k6 값(사용자 쪽), 원인 분석은 서버 지표로 한다.

| SLI | 기준 | 근거 |
|---|---|---|
| 응모 API p95(k6) | 1초 이하 | 사용자 체감 기준(흐름이 끊기지 않음) |
| 응모 성공률 | 99.9% 이상 | 오류 예산 0.1% |
| 처리량 | 초당 80건 | 1차 DB 반영 한계(초당 100\~110건)의 약 75%. 장시간 유지·GC·순간 지연에 대비한 여유 |
| DB 반영 완료 p95 | 1초 이하 | 응모 직후 내역·잔액 화면이 DB를 읽으므로 바로 열어도 보여야 한다 |
| 마감 시각 → CLOSED | 15초 이내(초당 80) | 스케줄러 주기 최대 10초 + 여유 |
| 중복·음수 잔액·cutoff 누락 | 0건 | 불변 조건. 1건이면 실패 |

범위: 응모, Stream 소비(DB 반영), 마감·Drain, Snapshot, 추첨, 동시 요청, 정합성 검증. 적립·게시글·댓글·구독 인증·퀴즈·로그인은 제외한다.

## 3. 차수별 결과

### 3.1 1차 → 2차: 기준선에서 찾은 문제

| 찾은 문제(1차) | 조치 | 1차 | 2차 |
|---|---|---|---|
| DB 반영 처리량 한계. Stream 소비자 1개가 메시지를 순서대로 반영(건당 약 10ms). 같은 구간 서버 CPU 74% 이하, RDS CPU 38% 이하, DB 연결 대기 0으로 자원은 여유 | 서버당 소비자 4개, 한 번에 10건(BE #697) | 초당 100\~110 | 초당 200\~250 |
| 초당 150 마감 몰림에서 Drain 지연 | 위와 같음 | 마감 → CLOSED 약 117초(Drain 112초), DB 반영 1초 이내 0.1% | 6.4초(Drain 55ms), 1초 이내 100% |
| Redis 메모리 계속 증가. 보호 키는 이벤트 종료까지, Stream은 정리 없음. noeviction이라 상한에 닿으면 응모 실패 | 보호 키 70분, 반영된 Stream 항목 정리(30초마다 `XTRIM MINID`), 다시 차감 되돌리기(BE #685) | 지속 20분 +48MiB(분당 약 2.4MiB), 계속 증가 | +10.9MiB, 키 TTL로 상한 |
| 후보 약 9,400명부터 추첨 실패. 1만 명 입력 68,914바이트 > TEXT 65,535바이트 | 추첨 입력·출력 MEDIUMTEXT(BE #669) | 1만 명 500 오류 | 1만 명 606\~1,269ms, 재현 검증 VERIFIED |

- 그 밖에 2차 이미지에 포함된 변경: 소비자 정리 오류 전달(BE #689), Redis 연결 풀(BE #699), CI 배포 순서(BE #700)
- 개선 요인 확인: 같은 이미지·같은 DB 상태에서 소비자만 1개로 줄이면 반영 처리량은 초당 약 80이다. 한계가 오른 것은 소비자 수 때문이다
- 한계가 앱 서버 CPU(2코어)로 옮겨 갔다. 초당 250에서 서버 CPU 86%, DB 연결 10개 소진·대기 발생
- 대가: 낮은 부하의 API p95가 올랐다(초당 150 기준 17ms → 29ms). 소비자 4개가 API와 CPU를 나눠 쓴다. SLO(1초)와는 거리가 멀다
- Redis 응모 키 상한(계산값): 초당 R건이 70분 넘게 이어지면 보호 키·idem 키가 R × 7,800개에서 멈추고 메모리는 R × 1.7\~2.1MB. 256MiB 상한이면 초당 100 이상이 1시간 넘게 이어질 때 한도에 닿는다

### 3.2 2차에서 새로 찾은 것: 정각 DB 멈춤

부하 중 매 정각에 DB 서버가 1\~4초 멈추고, 응모 API도 DB 연결을 기다리며 함께 멈췄다. 응모 API는 Lua 전에 DB를 조회하는 단계가 있어 DB가 멈추면 같이 멈춘다.

| RDS 클래스 | 정각 0\~3초 RDS CPU steal | 스왑 | 응모 API 최대 |
|---|---|---|---|
| db.t4g.micro(1GiB) | 47\~62% | 관리 프로세스 메모리 약 +370MB, 스왑 쓰기 발생 | 1.1\~4.1초(정각 4회 재현) |
| db.t4g.small(2GiB) | 최대 60% | 0 | 3.87초 |
| db.m6g.large(비버스터블) | 0% | - | 1.31초(DB 멈춤 없음) |

- 메모리·스왑은 micro에서 멈춤을 키운 요인이고, 2차 결론은 버스터블 RDS의 정각 CPU steal이었다
- m6g.large에서 남은 1.3초는 앱 서버(t4g.small)의 정각 steal(최대 37%)이다
- 조치: 운영 RDS는 db.t4g.small 유지(서울 단일 AZ 월 약 $37, db.m6g.large 약 $153, 다중 AZ는 두 배). 대신 응모 경로의 프로필 검사 DB 조회를 없앴다(BE #707). 운영 부하 테스트에서 다시 잰다
- 함께 찾은 것: 부하 테스트·개발 DB(micro)의 `innodb_buffer_pool_size` 128MiB, `max_connections` 60. 운영 small은 512MiB, 137

#### 정각 마감(t4g.small 앱 서버)

운영 RDS(db.t4g.small 다중 AZ)의 정각 steal은 13:00 몰림 중 0\~1.5%, 매시 관찰에서 최대 14.1%(1초)로 2차(47\~62%)보다 작았다. RDS steal 없이도 정각 DB 쓰기는 멈췄고, 앱 서버에서 정각 steal이 나타났다.

| 측정 | 결과 |
|---|---|
| 13:00 정각을 지나는 마감 몰림(초당 150, 마감은 정각 18초 뒤) | 정각 0초 API p95 1,160ms·최대 1,506ms. 마감 1초 전까지 최대 1,851ms. DB 반영 1초 이내 91.9%(SLO 미달) |
| 대조 마감(정각 아님, 같은 부하) | API p95 19ms·최대 182ms. DB 반영 1초 이내 100% |
| 16:00:00 정확한 정각 마감(초당 150) | 정각 0\~3초 앱 서버 steal 최대 79%·45%, 같은 시각 k6 서버(c7g) 0%. +0초 API p95 1,553ms·최대 2,009ms. 마감 전에 보냈는데 거절 1건(마감 3ms 전), 마감 뒤 성공 0. DB 반영 1초 이내 100% |

- steal이 오른 초에 앱 서버 us·sy는 오르지 않았다. 서버 안 작업이 아니라 CPU를 하이퍼바이저 쪽에 뺏긴 것이다. 무제한 크레딧이고 크레딧이 남은 서버도 같아 크레딧 부족도 아니다
- RDS도 부하와 무관하게 매시 약 2초 동안 관리 프로세스와 커널(sys)이 vCPU를 거의 다 쓴다(idle 5\~9%). 쓰기 중이면 쓰기 IOPS가 22\~25%로 떨어진다
- 정각에 steal이 생기는 원인과 RDS 매시 작업의 내용은 AWS 호스트 안쪽이라 확인하지 못했다
- 영향이 큰 경우는 응모가 몰리는 중에 정각을 지나는 이벤트다. 정확히 정각에 끝나는 이벤트는 멈춘 요청 대부분이 마감 뒤 요청이라 영향이 작다

### 3.4 어뷰징 탐지 켬·끔

응모 API에 어뷰징 탐지를 켰을 때의 비용과, 부하 중 탐지 결과가 부하 없을 때와 같은지를 본다. 초당 80 × 11분(앞 1분 제외)을 끔·켬 번갈아 3회씩, 중앙값으로 비교한다. 임계값은 시험용(1초 윈도)이다.

| 항목 | 끔 | 켬 | 차이 |
|---|---|---|---|
| k6 p50 / p95 / p99 | 7 / 13 / 49ms | 8 / 14 / 50ms | 각 +1ms |
| 서버 측 응모 API 평균 | 7.12ms | 7.52ms | +0.41ms |
| 응모 1건당 Redis Lua 호출 | 1회 | 2회 | +1회(약 0.4ms) |
| 서버 CPU | 33.3% | 36.0% | +2.7%p |
| DB 반영 1초 이내 | 100% | 100% | 차이 없음 |
| 실패 | 0 | 0 | - |

- 탐지는 요청마다 Lua 1회이며 임계값과 무관하다. 요청 스레드에서 동기로 실행된다
- 피크(초당 160 × 90초, 각 1회): p95 13ms로 같고 CPU 54.8% → 59.3%(+4.5%p)
- 정확도: 탐지 대상 5가지 패턴을 부하 없음과 부하 중에 주입해 탐지 9건이 회원·종류까지 같았다. 정상 회원 탐지 0건(켬 상태 요청 약 23만 9천 건)
- 탐지 키는 (윈도 + 60초) 동안 응모한 (회원, 이벤트) 조합 수만큼 생긴다. 초당 80에서 4,200\~4,344개, 약 0.55MB
- 운영 추정: 운영 ElastiCache(TLS)의 앱 쪽 Lua 평균이 이 환경보다 0.34ms 길어, 켬은 응모 1건당 약 0.7\~0.9ms 늘어날 것으로 본다(측정값 아님)

## 5. 한계

- 1차는 시나리오마다 1회 측정이다. 같은 조건의 값이 고르게 나와(초당 80 p95 15\~20ms) 1회로 기준선을 삼았다
- 2차에서 소비자 하나의 처리량이 1차보다 약 20% 낮았다(메시지당 약 9.5ms → 12ms). 쌓인 응모 행이 버퍼 풀(128MiB)을 넘은 것이 후보이고, 원인은 가르지 못했다
- Redis 응모 키 메모리 상한은 키 측정으로 계산한 값이다. 1시간 지속 측정은 하지 않았다
- 정각 CPU steal과 RDS 매시 관리 작업의 원인은 AWS 호스트 안쪽이라 확인할 수 없다. 공개 자료에서도 원인을 밝힌 곳은 찾지 못했다
- 3차 한계는 넓게(단계마다 1분)만 측정했다
- 3차 소비자 건당 시간이 2차보다 긴 원인(다중 AZ 동기 복제)은 확인 전이다
- 서버 4대에서 RDS CPU가 다음 병목이 되는지는 계산만 했고 측정하지 않았다
- 복제 확인의 p95 증가분은 JIT 미예열, c6g 교체와 나누지 못했다
- c6g.large 이후 정각 지연(최대 253ms)의 원인(이벤트 캐시 만료 때 동시 DB 읽기)은 코드 확인 전이다
- 앱 서버 2대가 같은 마감을 동시에 처리할 때 상태 전이를 두 서버가 함께 하는지는 확인하지 않았다. Snapshot은 DB 고유 제약으로 하나만 남는다
- 어뷰징 탐지
  - Redis가 앱 서버 안 컨테이너라 왕복 시간이 운영(ElastiCache TLS)보다 짧다
  - 임계값은 시험용 1초 윈도다. 키 수·메모리·탐지 빈도는 운영 값에 따라 달라진다
  - 응모 경로만 측정했다. 미션 완료·구독 인증 경로의 규칙은 다루지 않았다
  - 정상 회원 오탐 0은 부하 스크립트가 회원의 연속 요청을 서로 다른 이벤트로 보내도록 짜여 있어 구조상 예상된 값이다. 실제 사용자 분포의 오탐은 알 수 없다
  - 피크는 끔·켬 각 1회다
  - 탐지는 기록만 한다. 응모·당첨·계정에 자동으로 걸리는 제한은 없다
